# Собрать, проверить и выпустить мод

[English](RELEASE.md)

## Что коммитить

Откройте в Git-клиенте **эту папку**, где лежат `Release.cmd`, `manifest.json` и `src`. Это корень репозитория мода. Исходники находятся в `src/`. Не выбирайте родительскую папку с историей разработки.

Коммитьте разрешённые `.gitignore` папки `src/`, `assets/`, `Translations/`, `Screenshots/`, `tests/`, `tools/`, `third_party/`, `.github/`, корневые скрипты сборки, примеры настроек, документацию и лицензию. `outputs/` и `release.local.json` исключены. Готовые ZIP прикладываются к выпускам, а не добавляются в исходники. Отправьте эту папку в [rizias/valheim-boombox](https://github.com/rizias/valheim-boombox).

Скриншоты и полные руководства игрока на английском и русском остаются в репозитории. Установочный ZIP содержит английский README со ссылками в GitHub, без копий скриншотов и полных руководств. Thunderstore отображает README из загруженного ZIP. Адреса его картинок ведут в GitHub. Перед публикацией пакета отправьте связанные файлы в `main` и сделайте репозиторий публичным. Приватный репозиторий не предоставляет картинки другим игрокам.

## Локальная сборка одной кнопкой

1. Закройте редакторы, которые могут одновременно сохранять исходники.
2. Дважды щёлкните **`Release.cmd`**.
3. Дождитесь `Verified release` либо `Reused verified release`. При ошибке архив не считается готовым.
4. Возьмите ZIP по выведенному пути `outputs/local/<версия>/<отпечаток сборки>/Rizias-ValheimBoombox-<версия>.zip`. Рядом лежит файл `.zip.sha256`.

Отдельный `Rizias-ValheimBoombox-<версия>-FFmpeg-Sources.zip` содержит соответствующие исходники FFmpeg и инструкции сборки. Он публикуется рядом с установочным ZIP со своей контрольной суммой. Архив исходников не нужно устанавливать или загружать на Thunderstore как пакет мода.

FFmpeg/ffprobe распространяются по LGPL 3.0 или более поздней версии на основании разрешения авторов выбирать позднюю версию лицензии. Перед загрузкой мода на другую площадку опубликуйте оба архива в публичном выпуске GitHub. Проверьте, что прямая ссылка на исходники из упакованного README скачивается без входа в аккаунт. Сохраняйте доступ к исходникам при распространении программ. Выбранные условия допускают другой сервер исходников согласно разделу 6(d) GPL 3.0, включённой в LGPL 3.0. Сохраняйте приложенные тексты лицензий и уведомление. Лицензия мода остаётся MIT.

Перед первой локальной сборкой настройте `release.local.json` по следующему разделу. Кнопка компилирует DLL, запускает офлайн-тесты именно этой DLL и проверяет состав и хеши ZIP. Игра, Gale и загрузка на сайты не запускаются.

Локальная сборка сохраняет номер версии из исходников. Она не меняет manifest, версию плагина, README, руководства и списки изменений. Собирайте сколько угодно раз. Изменённые входные файлы дают отдельный каталог локальной сборки; неизменённые переиспользуют проверенный архив. Старые результаты сохраняются. Отпечаток сборки обозначает точный набор входных файлов независимо от номера релиза.

Выбирайте `patch`, `minor` или `major` только при запуске **GitHub Actions → Release**. Задание рассчитывает следующий номер от наибольшей версии опубликованного обычного релиза. Локальные номера сборок, черновики и предварительные выпуски не учитываются. Например, после опубликованной `0.2.7` выбор `patch` выпустит `0.2.8`, даже если в исходниках остался больший номер от прежних локальных сборок. Обычный push запускает проверки, не публикуя мод и не повышая версию.

## Настройка после клонирования на другой компьютер

Нужны Windows x64, установленная Valheim, совместимый BepInExPack Valheim 5.4.2351, PowerShell 7, .NET SDK 10 с runtime и reference pack. Игра и библиотеки не входят в Git.

Скопируйте `release.settings.example.json` в **`release.local.json`** рядом с `Release.cmd`. Замените четыре значения действующими абсолютными путями:

| Поле | Что указать |
|---|---|
| `GameManaged` | `valheim_Data/Managed` установленной игры, с `assembly_valheim.dll`. |
| `BepInExCore` | Папка `BepInEx/core`, с `BepInEx.dll` и `0Harmony.dll`. |
| `FFmpegRoot` | Полный дистрибутив с `bin/ffmpeg.exe`, `bin/ffprobe.exe`, manifest, лицензией и `Sources`. |
| `PwshPath` | Файл `pwsh.exe` установленного PowerShell 7. |

Пример формата путей уже есть в JSON. Слеши Windows в JSON удваиваются. Этот файл остаётся локальным. Для FFmpeg используйте [материалы пересборки](third_party/ffmpeg/README.md). Взятые из установочного ZIP `Tools/FFmpeg/ffmpeg.exe` и `ffprobe.exe` для сборочного дистрибутива кладутся в `bin/`; остальные файлы и `Sources/` сохраняются рядом с `bin/`. Нельзя подставлять случайную сборку FFmpeg: упаковщик сверяет хеши с её манифестом.

## Сначала проверить локально через Gale

1. Откройте Valheim в Gale и создайте **новый тестовый профиль** через `Profile → Create new profile`. Рабочий профиль не изменяйте.
2. Установите в него BepInExPack Valheim, указанный в зависимостях мода.
3. Выберите **`Import → …local mod`**, затем готовый ZIP по пути локальной сборки, который вывел `Release.cmd`. Это импорт мода, не импорт профиля и не DLL отдельно.
4. Проверьте, что в тестовом профиле одна запись Valheim Boombox нужной версии. Для первого теста не добавляйте другие моды. Extra Slots необязателен.
5. В настройках запуска **тестового профиля** задайте отдельную папку сохранений через `-savedir "полный путь к отдельной папке"`. Например, `-savedir "C:\ValheimBoombox-TestSaves"`. Папка должна быть доступна для записи. Для самого теста создайте нового локального персонажа и новый локальный мир. Отдельный профиль модов сам по себе сохранения не изолирует.
6. Нажмите **`Launch modded`**. Запуск из Steam без Gale не проверяет этот профиль.
7. После загрузки проверьте нужные вам действия. Краткий проход ниже рассчитан примерно на две минуты, когда предметы уже подготовлены. Полный игровой прогресс в эти две минуты не входит.

| Проверка | Что должно получиться |
|---|---|
| Надеть аппарат, открыть инвентарь и нажать «Магнитофон» | Меню читается, панель перемещается, индикаторы не закрывают карту. |
| «Папки», добавить небольшую папку музыки, создать плейлист, «Слушать плейлист» | Трек слышен, пауза и продолжение работают, динамики реагируют. |
| Включить режим звука компьютера и запустить внешний плеер | Эффекты реагируют на основной мультимедийный выход Windows, звук не воспроизводится второй раз. |
| Выключить отдельные визуальные эффекты во вкладке «Эффекты» | Соответствующая визуализация исчезает; это отдельно от игровых бонусов. |
| Включить личный режим «Только музыка» во вкладке «Бонусы» | Аппарат перестаёт давать собственные игровые действия, музыка продолжает работать. |
| Снять и надеть щит, пройти и пробежать | Проверьте положение аппарата и отсутствие прежних рывков. |
| Выйти и снова открыть тестовое сохранение | Предмет и его настройки сохраняются; в журнале нет новых исключений мода. |

Крафт, кассета и все цепочки улучшений описаны в [руководстве игрока](PLAY.ru.md). Данная сборочная команда не подтверждает визуальную, звуковую или сетевую приёмку. `BUILD-INFO.json` внутри ZIP честно содержит `gameTested: false`. Локальный одиночный тест не заменяет проверку настоящей сетевой сессии. Серверу и клиентам нужна одинаковая версия.

Если найден баг, сохраните версию, шаги, ожидаемый и фактический результат. Журнал находится через `File → Open profile folder`, затем `BepInEx/LogOutput.log`. Перед публичной отправкой уберите личные пути, ID и сведения о музыке. Не публикуйте неисправный кандидат как проверенный релиз.

## Куда загружать

**Thunderstore и Hexium размещают мод. Gale является менеджером установки.** После локальной проверки запустите GitHub Release и скачайте установочный ZIP опубликованной версии для распространения. Один и тот же опубликованный ZIP загружается на обе площадки. Локальные тестовые архивы не являются опубликованными релизами. Не используйте GitHub-кнопку Download source ZIP как установочный архив.

### Thunderstore

1. Войдите в свой аккаунт и откройте [Upload package](https://thunderstore.io/package/create/).
2. В `Upload file` выберите готовый ZIP.
3. В `Team` создайте или выберите свою команду `Rizias`. Доступность имени определяется площадкой; файл ZIP сам команду не создаёт.
4. В `Communities` выберите **Valheim**. Выберите подходящие категории, включая **AI Generated** для этого проекта.
5. Просмотрите описание, версию и выбранную иконку. Нажмите **Submit**.
6. После обработки откройте страницу мода и проверьте README и скачиваемую версию. Сохраните ссылку для пользователей.

Формат уже готовится согласно [правилам пакета Thunderstore](https://wiki.thunderstore.io/mods/creating-a-package). Имя пакета в manifest остаётся `ValheimBoombox`; префикс автора задаётся командой площадки. Для обновления сохраняйте команду и имя пакета, загружайте новую версию.

### Hexium

1. Откройте [страницу отправки Valheim](https://valheim.hexium.gg/submit) и войдите через предложенный способ.
2. Выберите загрузку готового ZIP. Используйте тот же архив, что для Thunderstore.
3. Выберите свою команду и установку **на клиенте и сервере** (`both`). Проверьте описание и версию перед публикацией.
4. После обработки проверьте страницу и загрузку мода. Каждая версия загружается один раз.

Hexium принимает совместимые ZIP размером до 512 МБ. Сохраняйте приложенные тексты лицензий и прямую ссылку на исходники. Сначала опубликуйте отдельный архив исходников FFmpeg в GitHub, как описано выше. Особенности зависимостей описаны в [официальной инструкции Hexium](https://hexium.gg/packaging).

### GitHub

**Выпуск запускается в GitHub: Actions → Release → Run workflow.** Выберите ветку `main`, затем `patch`, `minor` или `major` и подтвердите запуск. Дальше сборка, тесты, обновление версии, тег и прикрепление архива выполняются автоматически.

Перед первым запуском отправьте исходники **этой папки** вместе с `.github/workflows/release.yml` в [rizias/valheim-boombox](https://github.com/rizias/valheim-boombox). Workflow появится во вкладке Actions после push. Ключи и ручная загрузка бинарных файлов не нужны: задание использует штатный `GITHUB_TOKEN` с правом `contents: write`.

Перед выпуском закоммитьте и отправьте изменения кода и заметки в разделе `[Unreleased]` файла `CHANGELOG.md`. Задание работает с отправленным коммитом `main`. Оно:

1. Проверяет коммит и наличие заметок, затем рассчитывает выбранный шаг от наибольшей версии опубликованного обычного релиза до загрузки зависимостей.
2. Получает библиотеки выделенного сервера Valheim и BepInEx во временном Windows runner GitHub. FFmpeg собирается из исходников с проверенным SHA256; готовый инструментарий кэшируется.
3. Проверяет декодирование звука, собирает DLL и запускает офлайн-тесты через `release.ps1`.
4. Проверяет архив и соответствие файлов версии результатам сборки.
5. Само коммитит файлы версии от имени `rizias` с GitHub noreply-адресом и отправляет тег `v<версия>`.
6. Создаёт GitHub Release с заметками этой версии из CHANGELOG, загружает установочный ZIP, архив исходников FFmpeg и обе контрольные суммы, сверяет размеры и серверные SHA256 всех четырёх файлов и публикует обычный выпуск с отметкой **Latest**.

Все тяжёлые операции выполняются на runner GitHub. Ваши Gale, игра и сохранения в этом процессе не используются. Успех подтверждается зелёным заданием Release и опубликованным архивом во вкладке Releases. Принятый запрос запуска ещё не означает успешный выпуск.

Если удобнее запускать из папки проекта, дважды щёлкните **`PublishGitHub.cmd`**. Это короткая команда запуска того же GitHub Actions, а не локальная сборка. Для неё установленный GitHub CLI должен иметь доступ к репозиторию. Для проверки подключения без запуска задания:

```powershell
.\PublishGitHub.cmd -CheckOnly
```

Обычный запуск кнопки выбирает `patch`; `PublishGitHub.cmd -Increment Minor` выбирает `minor`. `Release.cmd` остаётся локальной сборкой для проверки через Gale. Настоящий выпуск запускайте после своей проверки мода. Видимость репозитория не меняется; загрузки на Thunderstore и Hexium этот workflow не выполняет.

`PublishGitHub.cmd` вызывает `dispatch-release.ps1` для запуска workflow. Задание вызывает `publish-github.ps1`, который проверяет сборку, коммитит файлы версии, отправляет тег и загружает файлы выпуска. Учётных данных в этих файлах нет. Запуск использует твой вход в GitHub CLI, а облачное задание использует `GITHUB_TOKEN` своего репозитория. [Для запуска workflow нужны права записи](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow). Скачивание исходников не даёт другому человеку права отправлять изменения или выпускать версии в этом репозитории.

При изменившейся ветке или существующем целевом теге без соответствующего черновика запуск останавливается. Если у рассчитанной следующей версии остался незавершённый черновик выпуска, Run workflow продолжает именно её без изменения тега и повышения версии. От исходников тега могут отличаться только исправления механизма публикации; изменения самого продукта останавливают восстановление. Загруженные файлы должны совпадать по хешам и не перезаписываются. Архивы и черновики автоматически не удаляются.

Workflow использует [штатную авторизацию GitHub Actions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token) и [команды GitHub Releases](https://cli.github.com/manual/gh_release_create). Офлайн-тесты и проверка декодера не подтверждают игровой рендер, звуковое устройство или живой мультиплеер.

Для обратной связи включите Issues репозитория и дайте ссылку на странице мода. Просите версию и конкретные шаги воспроизведения.
